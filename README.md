# 91546LED — reverse-engineered RC car light protocol

Both data protocols of the **91546LED** RC car lighting boards, decoded and verified.
These boards are found in the **ZLL SG216** 1/16 drift car and likely in other models
using the same lighting set.

The boards are silkscreened `91546LED-A`, `-B` and `-F`. The vendor name **Runchen**
appears on the `-F` only — the other two carry the type number alone. `91546LED` is
therefore the reliable identifier.

If you lost your transmitter, swapped the ESC, or want to drive these lights from a
microcontroller instead of the original receiver — this is everything you need. No
lookup table is required; the translation between the two protocols is a formula.

**Status:** decoded, reproduced and verified on working hardware. Both protocols are
generated by an ESP32 and all 36 effects come out correctly.

---

## The chain

    Receiver ──> 91546LED-F ──> 91546LED-B ──> 91546LED-A ──> LEDs

| Board | Function |
|---|---|
| `Runchen 91546LED-F V1.1` | Voltage regulator. Drives the always-on taillights and the police light. **Passes the data signal through unchanged.** |
| `91546LED-B V1.1` | **Translator and distributor.** Converts the receiver protocol into the `-A` protocol. Outputs labelled `L1 + − L2`, `R+` and neutral ones. |
| `91546LED-A V1.1` | Carries the LEDs (one white plus a red ring) and **generates the animations itself.** |

Both `-F` and `-B` carry a **78M05** linear regulator.

**Both `-F` and `-B` can be removed entirely** if you drive the `-A` boards directly —
see [Driving the -A directly](#driving-the--a-directly).

### The -B outputs are channel-bound

They are labelled `L1 + − L2`, `R+`, plus neutral terminals without L/R. Whatever hangs
on `R+` **necessarily blinks along with the right indicator**. If a lamp flashes when it
shouldn't, check which output it is on before you suspect the code.

## Protocol 1: Receiver → -B

| | |
|---|---|
| Idle level | **HIGH** |
| Unit time | **1062 µs** |
| Structure | 9 symbols, each 1 or 2 units, **11 units total** |
| Code | the positions of the **two long** symbols |
| Frame period | **116478 µs** (8.585 Hz) |
| Active part | 11.68 ms |

This protocol transmits **pulse widths, not one bit per unit time.** Exactly two of the
nine symbols are long, and their positions carry the mode.

A pulse of 3 or more units is invalid — the board discards the frame. Hence there are
C(9,2) = **36 valid frames**.

Connector wiring: **white = GND, red = signal, black = +8 V.** This matches no common
convention. Measure, don't guess by colour.

## Protocol 2: -B → -A

| | |
|---|---|
| Data line | **pin 1** (`L1` on the `-B`, `1` on the `-A`) — pin 2 carries nothing |
| Idle level | **LOW** |
| Unit time | **509 µs** (measured 510.2 µs at 10 MS/s) |
| One bit | 4 units: `H3 L1` = 1, `H1 L3` = 0 |
| Frame | 8 bits plus a trailing H of 1 or 3 units |
| Frame period | 117 ms, same as the input |
| High level | **3.657 V** — not 5 V |

So: inverted idle level, halved unit time, different symbol widths, same period. The
ratio of unit times is 1062/509 = **2.087**, almost exactly 2:1 — probably the same base
clock with a different divider.

**Pin 2 is not needed.** Proven on the working system: pin 2 between `-B` and `-A` was
cut, and several effects kept working.

### The translation formula

From the two long positions `(a,b)` of the input frame:

    bit 1        always 1                          start marker
    bit (2+a)    set
    bit (2+b)    set, if b <= 7
    trailing H   3 units instead of 1, if 6 or 7 is in (a,b)

Checked against all 36 measured frames: **zero deviations.** A reference implementation
is in [`example/translate.c`](example/translate.c).

**Limit of the format:** the data field is only 8 bits wide. `(6,7)` and `(6,8)` therefore
produce the same code `100000011` — the `-A` cannot tell them apart. The 36 input frames
map onto only **35** distinct codes.

### No hidden fine structure

A triggered capture at **10 MS/s** (0.1 µs resolution) shows only three run lengths
within the 1.64 ms window and no pulse shorter than 50 µs apart from the trigger point.
The edges are clean; there are no hidden synchronisation pulses. The signal model is
complete.

## The OFF code: `000000000`

A frame **without the start bit** — eight zero bits, each sent as `H1 L3` — is rejected
by the `-A` as invalid and turns it **dark immediately**, not after a timeout.

This is the key to arbitrary blinking. Any of the 35 effects can be alternated against
black, down to one frame (116.5 ms) per phase.

**There is no OFF through the `-B`.** Tested with both kinds of invalid frame:

| Input to the `-B` | Behaviour |
|---|---|
| **valid** frame | sends the corresponding code |
| **invalid** frame, signal present | holds the last mode and **keeps sending** — lights stay on |
| **no signal**, line idle | stops sending → the `-A` goes dark after its own timeout (> 349 ms) |

Verified with four transitions of 5 s each, for both invalid frame types:

- **`11001011010`** — no frame start (begins high; all symbol widths valid). Lights stayed on.
- **`01111011010`** — contains a **4-unit** pulse, i.e. an invalid symbol. Lights stayed on.

**Important consequence for your own firmware:** if you blink by holding the line idle,
short dark phases are invisible — the `-A` needs more than 349 ms of silence before it
goes out. Send the OFF code instead; it acts within one frame.

---

## Nothing latches

The mode is not stored anywhere. If the input goes quiet, the `-B` stops sending (pin 1
at 0.002 V, zero edges, measured four times) and the `-A` goes dark.

**Your controller must repeat the frame every 117 ms, permanently.**

## Driving the -A directly

    GPIO ──> pin 1 of the LEFT  -A       data, 3.3 V push-pull, 509 µs unit time
    GPIO ──> pin 1 of the RIGHT -A
    3.3 V ──> + of both boards
    GND   ──> − of both boards, common ground

3.3 V push-pull is enough. The `-B` itself only drives **3.657 V**, and the `-A` runs off
a 3.3 V supply. No level shifting needed.

**Two independent channels.** Driving both pins in lockstep within one frame works
because the edges sit at 1 and 3 units inside each bit — so one channel can send a 1
while the other sends a 0 without the timing drifting apart. That gives **arbitrary
combinations** of the 35 codes, e.g. Knight Rider on the left and steady red on the right.
The `-B` could blink left and right separately (`(3,6)` / `(3,7)`) but only in the roles
its firmware provides.

**No hidden modes.** All **221** codes with the start bit set that the `-B` never produces
were sent, 4 s each. Not a single new effect. Dropping the `-B` saves a board but gains no
functionality. Not tested: the 256 codes without a start bit, presumed invalid.

**On the supply:** if both `-A` boards hang on a controller board's 3.3 V rail, its
regulator may reach its limit. Flicker or resets when connecting the second board point
that way — use an external supply then.

There the second position controls the **red ring**:

| long at | red ring |
|---|---|
| 3,4 | fade / breathing |
| 3,5 | Knight Rider |
| 3,6 | one side blinks |
| 3,7 | other side blinks |

### The two running-light frames

| long at | running light | white LED |
|---|---|---|
| 3,5 | yes | **off** |
| 5,8 | yes | **on** |

### Steady images vs. animations

If you want to alternate two codes without any animation running, pick **steady** ones.
`4,8` is "everything on", `4,5` is "red ring only, white off" — both are still images.
`3,5` also switches white off but brings the ring's Knight Rider animation with it, which
the `-A` generates on its own and which cannot be suppressed.

## What was ruled out

Listed so nobody spends time re-testing it:

- **"11 independent bits, bits 2/6/7 have no effect"** — wrong. Setting bits 2 and 3
  together produces a 4-unit pulse and thus an invalid frame. The protocol transmits
  pulse widths, not one bit per unit time.
- **"First long position selects the colour, second the effect"** — wrong, disproved by
  the aliases (0,6)==(4,6) and (3,7)==(4,7).
- **"(6,7) is running light without white"** — wrong, it is steady light.
- **"The `-F` is a protocol translator"** — wrong. It is a voltage regulator and
  taillight driver, and passes the signal through.
- **"The `-B` latches the mode"** — wrong, it stops sending. What had been observed was
  only that the lights stayed on during a servo sweep, where a signal was present at the
  input but no valid frame.
- **"The `-A` needs 5 V, a 3.3 V GPIO is not enough"** — wrong. The `-B` itself only
  drives 3.66 V and the `-A` runs off 3.3 V. An open-drain workaround with a pull-up was
  unnecessary, and was not even a valid test (the measurement showed zero edges because
  the pull-up was not on a live 5 V rail).
- **"The `-A` has hidden modes"** — wrong. 221 never-sent codes, no new effect.
- **"There is a return channel on the data line"** — implausible; there is nobody who
  could act on an acknowledgement.
- **"The fourth wire is an unused standard connector shell"** — inconsistent with the
  cost argument. Pin 2 is demonstrably dispensable; why it exists is still open.

## How it was measured

**Instrument:** Digilent Analog Discovery 2 via `libdwf`, driven from Python with
`ctypes`. Digital captures for timing, analog captures for real voltage levels.

Pitfalls worth knowing:

- The digital buffer holds only **4096 samples**. Choose a window longer than one frame
  period and cut the burst out between two long low phases — otherwise you capture
  truncated bursts and misread the frame structure.
- The analog buffer holds 16384 samples.
- A cheap FX2-based logic analyser (`fx2lafw`, 8 channels) also works for the timing, but
  min. 20 kHz sample rate and 24 MHz only single-channel.

**A warning from experience:** hours were lost to USB dropouts that looked like an
overvoltage problem or a broken analyser. The cause was a **charge-only USB cable.** If
captures abort, swap the cable before you suspect anything else.
